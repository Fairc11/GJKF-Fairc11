# 仓库公开与发布策略

## 先确认授权动作

| 用户表达 | 默认允许 | 不自动包含 |
|---|---|---|
| “提交到 Git” | 本地精确 commit | push、tag、PR、Release |
| “上传 GitHub 仓库” | 需要确认目标远程和源码范围 | 安装包、Release |
| “发布新版本” | 准备版本与验证 | 替换线上资产 |
| “发安装包” | 需要确认私域或公开渠道 | 公开 Release |

## 公开前审计

1. 确认真实 repo root 和远程地址。
2. 检查 `git status --short`，保护用户未跟踪文件。
3. 精确 `git add <files>`，禁止默认 `git add -A`。
4. 检查缓存区文件名和完整 diff。
5. 搜索已跟踪文件中的密钥、Cookie、个人路径、账号、真实档案统计和内部截图。
6. 判断是否需要检查 Git 历史；删除工作树文件不能清除历史泄露。
7. 分别审计源码仓库、二进制资产和 Release notes。
8. 核对 LICENSE：源码授权与维护者官方二进制发布政策不得混写。

## 分发矩阵

| 形式 | 典型内容 | 风险 |
|---|---|---|
| 公开源码 | 代码、构建配置、公开文档 | 历史密钥、个人路径、内部 handoff |
| 私域二进制 | DMG、EXE、校验文件 | 制作者登录数据、用户产物、未公证提示 |
| 公开 Release | 标签、安装包、说明 | 许可证、平台政策、长期维护和资产替换 |

## 发布顺序

1. 更新唯一版本源和用户文档。
2. 完成开发态、封包态和干净环境验证。
3. 精确提交并复核。
4. 用户明确授权后 push。
5. 用户明确授权后创建标签、PR 或 Release。
6. 上传后重新读取远程状态、资产大小和校验值。

准备资产不等于获准公开发布。用户确认前不得替换现有 Release 资产。
