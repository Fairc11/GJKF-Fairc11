# 交付形态与平台决策

## 先问清楚

- 谁使用：开发者、熟人、普通公众还是组织设备？
- 数据在哪里：本地文件、用户账号、远程服务还是公开数据？
- 是否需要系统能力：文件选择器、托盘、原生窗口、离线媒体、后台任务？
- 是否允许服务器：费用、运维、隐私和账号风险能否接受？
- 目标平台：Apple Silicon、Intel Mac、Windows、浏览器、移动设备？
- 分发方式：源码、本机自用、私域二进制、公开下载还是商店？

## 三类跨平台方案

### 保留现有后端，增加 Web 入口

适用于现有应用已经使用 HTTP API、模板或单页前端。改动通常最小，但必须判断服务运行位置：

- 本机 Web：每个用户仍需运行本地后端。
- 局域网 Web：一台可信机器持续运行，其他设备访问。
- 公网托管：真正跨平台，但引入服务器、账号、数据上传和合规成本。

### 分平台桌面壳，共用业务核心

适用于本地文件、账号隔离和离线能力重要的工具。保持 Python/业务核心，分别实现 macOS 与 Windows 的窗口、浏览器和打包适配。

### 迁移跨平台框架

Tauri、Electron、Qt 等适合长期维护多平台桌面产品，但不是“少改动”的默认答案。先估算：

- 业务核心能否复用；
- 登录浏览器和 Cookie 同步是否要重写；
- 构建、签名和更新系统是否成熟；
- 维护两套桥接代码是否比现方案更贵。

## 输出决策表

至少比较：现有代码复用率、缺失能力、首次开发量、长期维护、账号安全、用户前置条件、干净环境验收难度。明确推荐方案和不选方案的原因。
